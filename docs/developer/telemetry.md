# Журнал, ошибки и метрики

## Три разных назначения

| Механизм           | Назначение                                                 | Реализация в 1.0                                                            |
| ------------------ | ---------------------------------------------------------- | --------------------------------------------------------------------------- |
| ActivityService    | Административные действия, изменения, before/after и diff. | SQLite + JSONL, необязательная доставка в Discord.                          |
| ErrorReporter      | Ошибки, stack/cause, ID отчёта и повтор доставки.          | Дисковый outbox; supervisor, LOG_ID и резервный LOG_WEBHOOK.                |
| Prometheus/Grafana | Агрегаты, частоты, задержки и оповещения.                  | Отдельный Metrics-модуль пока не реализован. `/metrics` в этом выпуске нет. |

Не выдавайте наличие healthcheck или журнала за готовую интеграцию Prometheus. Проектирование будущего Metrics-модуля описано отдельно в [спецификации](../superpowers/specs/2026-10-30-ticket-and-metrics-design.md).

## Запишите действие

Используйте `activity.record(actor, input)` там, где известен результат операции. `actor` содержит `userId` и `name`; `input` — `kind`, `target`, `summary`, необязательные `details`, `before`, `after`.

```ts
activity.record(actor, {
  kind: 'example.settings.save',
  target: 'example',
  summary: 'Изменены настройки сервиса',
  before: publicBefore,
  after: publicAfter,
});
```

Передавайте только безопасную проекцию объекта. Не полагайтесь на то, что редактирование секретов распознает произвольное новое имя поля. Новые ключи/API-токены добавляйте в общий механизм редактирования до записи на диск и доставки в Discord.

UI-наблюдения и подтверждённые серверные операции — разные события. Нажатие кнопки не доказывает успех отправки. Не логируйте содержимое обычных Discord-сообщений, HTTP cookie, заголовки Authorization, OAuth-коды и токены.

## Пакетная запись

Событие получает UUID и сначала атомарно сохраняется в локальный outbox. Только Bot consumer отправляет записи через Redis Stream и фиксирует пачку до 100 событий в SQLite. Таймер — одна секунда. При недоступности Redis те же дисковые записи сохраняются напрямую пакетами.

ACK выполняется после персистентной записи. Уникальный UUID не допускает вторую строку события в SQLite; после потери подтверждения внешняя доставка/JSONL всё ещё могут повториться. Не удаляйте локальную очередь до фиксации и не переносите критические ID или изменения правил в этот поток.

Авторизацию не кешируют. Redis не является источником истины для настроек, сессий и публикаций.

## Отчёты об ошибках

Передавайте ошибку с ограниченным контекстом в `errors.report(error, scope, context)`. Общий обработчик команды уже создаёт отчёт: не дублируйте его в catch с немедленным rethrow без дополнительной причины. Ошибки очереди доставки не должны рекурсивно создавать такую же очередь.

Пишите `scope` по операции, например `example.refresh`; используйте ID ресурса вместо URL с секретом. Показывайте пользователю краткий результат и ID отчёта, полный stack оставляйте в закрытом журнале.

## Контракт для будущих метрик

При реализации Metrics-модуля используйте ограниченные наборы labels: module, operation, outcome. ID пользователя, тикета, канала, текст и URL создают высокую кардинальность и могут раскрывать данные — они не должны быть labels.

Измеряйте команды, длительность операций, сбои внешних сервисов, состояние workers и глубину очередей. Между workers нужен явный сбор/агрегация: локальный счётчик Web не виден Bot. Защитите endpoint и исключите двойную регистрацию collector при рестартах. Dashboard должен ссылаться на реально экспортируемые имена и единицы измерения.

Навык для этой работы: [open-bot-observability](../../skills/open-bot-observability/SKILL.md). Он отдельно обозначает существующие механизмы и будущее расширение.
