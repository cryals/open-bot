# Архитектура и данные

## Границы процессов

```text
Менеджер службы
    └── Supervisor
        ├── Bot worker ── Discord Gateway + REST
        │   └── Core / Help / Info / Ticket / Status / Watchdog / consumer
        ├── Web worker ── Fastify + OAuth + REST + React
        └── Metrics worker (optional) ── защищённый Prometheus HTTP

Bot + Web ── SQLite WAL / uploads / activity-outbox
Bot       ── Redis Stream (необязательно) ── пакетная запись SQLite + JSONL
Supervisor ── очередь ошибок ── LOG_ID / LOG_WEBHOOK
```

Только Bot владеет Gateway и обработчиком очереди активности. Web проверяет права через Discord REST и пишет события в общий дисковый outbox. Только supervisor доставляет error-outbox. Второй экземпляр с той же базой не является способом горизонтального масштабирования.

Heartbeat передаётся раз в 5 секунд. Supervisor перезапускает повреждённый worker с увеличением задержки; сам supervisor должен обслуживаться внешним менеджером службы. Таймауты, backoff и ограничения памяти описаны в [runtime-справочнике](../MODULES.md).

## HTTP и права

В `app.ts` API защищено серверной OAuth-сессией. Административная роль проверяется через Discord для каждого привилегированного запроса. Изменяющий запрос дополнительно требует совпадающий Origin и CSRF-заголовок. Сессии и OAuth states имеют срок действия, state привязан к cookie.

Не переносите проверку ролей в React и не кешируйте её в Redis. UI может скрывать кнопку для удобства, но решение принимает сервер. Добавляя новый публичный endpoint, явно определите его доступ и исключение из общего hook.

## Правила и публикации

`Store` хранит черновик с версией и неизменяемые опубликованные снимки. `Publisher` общий для Web и Info. Он валидирует содержимое, получает межпроцессную SQLite-блокировку, обновляет Discord и затем сохраняет результат. Активный снимок используется навигацией; `published-rules.ts` кеширует подготовленные страницы по ID ревизии.

Сохранение проверяет ожидаемую версию; устаревшая запись получает конфликт. Восстановление ревизии меняет черновик, а публикация остаётся отдельным действием. Нельзя связывать активное представление с несохранённым React-состоянием.

Discord и SQLite не образуют общую транзакцию. Nonce и персистентная попытка снижают вероятность дубликата, но не дают exactly once после длительной потери связи. Не делайте слепой повтор создания при неизвестном исходе.

## Общая модель Components V2

`src/shared/blocks.ts` задаёт текст, контейнеры, секции, медиа, кнопки, файлы и разделители. Её используют редактор, предпросмотр и серверная сериализация. Изменение схемы должно сохранять чтение старых текстовых правил, ревизий и шаблонов.

ID блоков стабильны, включая асинхронные загрузки. Сервер повторно проверяет лимиты и локальные media ID. Предпросмотр помогает редактировать, но окончательное ограничение применяет API.

## Хранение

SQLite работает в WAL с foreign keys и busy timeout. Миграции применяются автоматически до запуска рабочих процессов. Для изменений структуры добавляйте следующий файл миграции; не редактируйте уже применённые миграции.

Критические изменения правил, сессий, ID сообщений и публикаций фиксируются сразу. Только журнал активности допускает отложенную пакетную запись. `uploads/` и очереди расположены рядом с базой; резервная копия должна сохранять эти данные вместе.

Ticket history, lifecycle/access jobs, статусные наблюдения и Watchdog confirmations фиксируются сразу. Копии Ticket лежат в `ticket-files/` рядом с базой. Metrics пишет снимки раз в 10 секунд; exporter агрегирует процессы. Подробнее: [интеграции](integrations.md), [телеметрия](telemetry.md), [эксплуатация](../OPERATIONS.md).
