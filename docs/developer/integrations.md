# Ticket, Game Server Status и Watchdog

Модули зарегистрированы в общем catalog. Только Bot держит Gateway и фоновые обработчики Discord; Web записывает конфигурацию и намерения в SQLite. Redis используется для журнала, не для критических операций.

## Ticket: состояние и архив

`modules/ticket/store.ts` хранит конфигурацию, обращения и события. `service.ts` выполняет сохранённые стадии жизненного цикла, `archive.ts` — сообщения, ревизии и копии вложений. Миграция `007-modules.sql` добавляет эти таблицы вместе с общими настройками новых модулей.

```text
creating: channel → thread → control → staff-card
open / claimed / waiting
closing: freeze → archive → archive-thread → delete-channel
closed: 180 дней → purging → удаление ветки, файлов и записей
```

Ошибки сохраняют стадию и срок следующей попытки. Имена/topic и сохранённые ID используются для поиска уже созданных объектов; сообщения получают nonce. Discord не даёт общей транзакции с SQLite и бессрочного idempotency key. После неопределённого исхода длительного сбоя может потребоваться ручная сверка объектов.

Изменения участников и категории идут через `ticket_jobs`, одно задание на обращение. Восстановление возвращает прерванное running-задание в pending. Сначала меняются Discord permissions, затем локальное состояние. Закрытие не запускается поверх незавершённого изменения доступа.

История полученных сообщений и сырые снимки сохраняются синхронно. Правки текста, компонентов, embeds и состава вложений создают ревизии. Клиент не получает исходные signed CDN URLs. Копии файлов создаются отдельно с лимитом размера, таймаутом и запретом redirect; читаются только с фиксированных Discord CDN hosts. Inline-preview разрешён распознанным растровым форматам; остальные типы отдаются скачиванием.

События во время простоя не гарантированы. Reconcile восстанавливает оставшуюся историю через REST; `archive_gap` описывает пробел. Не выдавайте время обнаружения удаления за точное время неизвестного Gateway-события.

`access.ts` отделяет общую администрацию, Ticket manager и Ticket viewer. Автору запрещён staff scope независимо от роли. Ветка создаётся в отдельном закрытом родительском канале. Discord Administrator — внешнее исключение, которое бот не может устранить. Транскрипт не дублируется в бессрочном browser activity audit.

## Game Server Status

`statusUrl()` преобразует ss14/ss14s адрес с сохранением пути. Zod ограничивает ответ `/status`, body ограничен 256 КБ, timeout — 5 секунд. Кеш 15 секунд и single-flight принадлежат процессу. Наблюдения живут в SQLite и исполняются Bot worker раз в минуту.

`GAME_SERVER_HOSTS` — deployment allowlist точных хостов. Не превращайте его в разрешение произвольных URL из React. Redirect запрещён. Удаление конфигурации атомарно отключает наблюдения; удалённое Discord-сообщение создаётся заново.

## Watchdog

`power_operations` сохраняет actor, версию конфигурации, цель, действие, срок подтверждения и состояние. `pending → running` выполняется условным SQL UPDATE; unique index допускает одну running-операцию на экземпляр. Unknown блокирует новые и ранее подготовленные операции.

Подтверждение не переносится между пользователями. POST не повторяется после потери ответа. Interrupted running переходит в unknown; администратор подтверждает ручную сверку. Групповой перезапуск имеет отдельные результаты, максимум пять запросов одновременно.

В конфигурации хранится ENV reference `WATCHDOG_TOKEN_*`; секрет разрешается только сервером. Перед error delivery значения добавлены в redaction. Credentials в URL, redirect и хосты вне `WATCHDOG_HOSTS` запрещены. Не подменяйте отказ повтором POST без нового подтверждения.

## Локальная демонстрация

`npm run ui:modules` поднимает FakeDiscord и локальный SS14/Watchdog mock на 3320/3321. Входы `/__demo/admin`, `/__demo/manager`, `/__demo/viewer` показывают разные права. База в памяти, реальные сервисы не вызываются. Регрессии находятся в `tests/modules.test.ts`.
