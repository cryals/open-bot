# Производительность и UX

Изменения 2026-10-30 используют существующие механизмы; права доступа не кешируются и не ослабляются.

## Bot

- Опубликованная разбивка правил кешируется по номеру revision отдельно для каждой Store. Каждый запрос проверяет текущий revision ID; новая публикация видна сразу. Тексты черновика не попадают в кеш опубликованной версии. Сохраняется только последний снимок на Store.
- Проверка публикации вычисляет пагинацию один раз для каждого набора. Раньше цикл для каждой страницы заново разбивал весь набор: квадратичный объём повторной работы.
- Повтор команды проверяет cooldown/in-flight до REST-запроса прав. Обычная проверка роли для разрешённого административного действия сохраняется.
- Redis/outbox обрабатывает полные пакеты подряд с уступкой event loop между ними, чтобы очередь после всплеска не ожидала секунду на каждые 100 событий.

## Интерфейс

- Предпросмотр правил использует useDeferredValue и useMemo: полный пересчёт не обязан завершиться до отображения набранного символа.
- Повторные рендеры неизменённых блоков предпросмотра пропускаются через memo. Изображения вне экрана используют lazy loading и асинхронное декодирование. Автоопрос журнала не выполняется на скрытой вкладке.
- Фоновое обновление шаблонов/истории не меняет версию открытого черновика. Одновременные и устаревшие правки сообщения отклоняются до Discord PATCH.
- Ответ загрузки файла обновляет актуальный блок/элемент галереи по стабильному ID. Функциональное обновление документа сохраняет другие изменения; поздний ответ сохранения не перезаписывает загрузку, завершившуюся во время запроса.
- При обычной высоте окна sidebar имеет рабочую прокрутку списка и всей навигации. APP читается на белом фоне. Кнопки сохранения/публикации правил не показываются в настройках и истории.

## Измерение

Локальный Node.js/tsx, Windows, 2 набора по 100 логических страниц, по 20 одинаковых коротких предложений на страницу. Сравнены validatePayloads из b5515f8 и новая реализация; 3 последовательных замера, одинаковый документ:

| Реализация | Замеры, ms               | Медиана, ms |
| ---------- | ------------------------ | ----------- |
| До         | 491.77 / 433.93 / 417.50 | 433.93      |
| После      | 16.72 / 15.75 / 15.66    | 15.75       |

Это локальное время CPU-проверки большого документа, не задержка ответа Discord и не обещание такого же ускорения всего бота. Сеть Discord, права, обработка вложений и дисковая подсистема влияют на полный путь отдельно. Redis уменьшает число SQLite-транзакций, но сохраняет файловую запись каждого события ради восстановления.

Проверки реального Gateway и Redis в контейнере на этой машине не выполняются из-за известного ограничения виртуализации. Для Redis предусмотрен отдельный CI-тест с TEST_REDIS_URL. Ручная проверка UI использовала FakeDiscord и память, не живой сервер.
