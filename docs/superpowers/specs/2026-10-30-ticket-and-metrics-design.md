# Open Bot: Ticket и Metrics

Дата: 2026-10-30. Статус: требования уточнены с пользователем; проектирование подготовлено к рассмотрению. Реализация модулей — следующий этап.

## 1. Согласованные решения

- Каждый тикет — отдельный закрытый текстовый канал Discord.
- Роль `1565440922336886876` получает полный доступ к Ticket-модулю: панели, категории, сообщения, роли доступа, журнал, транскрипты и служебные обсуждения.
- Пользователь только с ролью `1565620276916658276` получает в веб-панели доступ к журналу тикетов и просмотру транскриптов. Он может участвовать в служебном обсуждении в Discord, но эта роль сама по себе не даёт права менять настройки или обрабатывать тикеты.
- Автор тикета не видит служебную ветку.
- Закрыть тикет могут автор, поддержка этого тикета и администраторы. Нужны причина и подтверждение.
- При закрытии сохраняется полный доступный архив: сообщения, правки, удаления и вложения. После успешного сохранения пользовательский канал удаляется, служебная ветка архивируется.
- Срок хранения — 180 дней после закрытия. Затем автоматически удаляются весь оперативный архив тикета, вложения и служебная ветка Discord.
- Prometheus и Grafana уже существуют. Нужны endpoint метрик и готовый dashboard JSON; новые экземпляры этих сервисов не разворачиваются.
- Брендинг интерфейса — Open Bot. Названия сообществ находятся в редактируемом содержимом.

## 2. Границы модулей

**Ticket** владеет конфигурацией тикетов, каналами обращений, служебными ветками, обработкой действий, сохранением переписки и сроком хранения. Его Discord-интерфейс использует Components V2. Настройки и архив доступны через Web с отдельными правами.

**Metrics** собирает показатели Core, Web, Help, Info, Ticket и будущих модулей. Экспортёр работает отдельным контролируемым процессом. Модули используют общий интерфейс телеметрии; успешная обработка обращения или команды не зависит от доступности экспортёра.

Существующие правила, опубликованные сообщения, сессии и данные не перезаписываются. Таблицы добавляются миграциями. Начальные настройки новых модулей задаются отдельно от текущих административных прав.

## 3. Веб-доступ

Вместо одной проверки «администратор панели» вводится проверка разрешений для каждого маршрута. Успешный OAuth-вход возможен при наличии хотя бы одного поддерживаемого доступа; это не предоставляет доступ ко всей панели.

| Возможность                                     | Полная роль Ticket                    | Роль просмотра                    |
| ----------------------------------------------- | ------------------------------------- | --------------------------------- |
| Список тикетов и поиск                          | Да                                    | Да                                |
| Просмотр переписки и событий тикета             | Да                                    | Да                                |
| Просмотр служебной переписки                    | Да, с ограничением для автора         | Да, с ограничением для автора     |
| Получение архивных вложений                     | В пределах доступного транскрипта     | В пределах доступного транскрипта |
| Изменение панелей, категорий, шаблонов          | Да                                    | Нет                               |
| Настройка ролей доступа к тикетам               | Да                                    | Нет                               |
| Административные действия над тикетом           | Да                                    | Нет                               |
| Настройки правил, сообщений и остальных модулей | Только при наличии прежних общих прав | Нет                               |

Существующий владелец и общие администраторы Open Bot сохраняют управление. Новые роли Ticket не становятся общими администраторами. При наличии обеих ролей действуют полные права Ticket.

Общая сессия возвращает разрешения для построения меню. Начальная загрузка интерфейса не запрашивает административные `/workspace` и `/guild` для пользователя, которому доступен только архив. Право проверяется заново на API-запросах, включая поиск, экспорт и выдачу каждого файла. Отзыв роли прекращает доступ без ожидания окончания сессии.

Служебная переписка дополнительно скрывается от автора тикета и в веб-архиве. Наличие Ticket-роли само по себе не отменяет это ограничение. Права владельца и `Administrator` в самом Discord технически позволяют обходить ограничения каналов; модуль не обещает скрывать Discord-данные от таких пользователей.

## 4. Панели и категории

Раздел Ticket содержит вкладки «Обращения», «Панели», «Категории», «Настройки». Веб-просмотр каждого тикета открывается по собственному адресу с проверкой доступа.

Редактор панелей использует существующие блоки Components V2 и предпросмотр. Появляется встроенное действие кнопки «Создать тикет». Его можно разместить в панели тикетов и в информационном сообщении. Опубликованные ID сообщений сохраняются; повторная публикация обновляет существующую панель.

Категория обращения хранит:

- стабильный ID, название, описание, эмодзи, порядок и доступность для создания;
- целевую Discord-категорию для пользовательских каналов;
- роли поддержки и явно выбранную роль для уведомления;
- начальное сообщение из блоков;
- необязательную настраиваемую форму перед созданием;
- шаблон имени канала в пределах ограничений Discord.

Стартовые категории можно предложить как «Вопрос», «Жалоба», «Обжалование», «Техническая проблема», «Заявка в команду», «Другое». Это редактируемые значения. По умолчанию форма не обязательна: как в примере Flow Bot, проблему можно описать внутри обращения.

Начальный лимит — один активный тикет на пользователя во всём сервере; ограничение и задержка повторного создания настраиваются. Повторный клик возвращает ссылку на существующий тикет. Создаваемая запись также учитывается как активная, чтобы параллельные запросы не обходили лимит.

## 5. Сценарий обращения

1. Участник нажимает «Создать тикет».
2. Получает личный список доступных категорий.
3. При необходимости заполняет форму категории.
4. Бот проверяет настройки, права, лимит и актуальность выбранной категории.
5. Создаёт канал с явными правами: автор, роли поддержки категории, бот и администраторы Discord. `@everyone` не получает просмотр.
6. Публикует карточку и начальное сообщение, сохраняет все ID. Разрешённое уведомление ограничивается выбранной ролью.
7. Создаёт связанную служебную ветку и карточку обращения в закрытом служебном канале.

Карточка показывает номер, категорию, автора, статус, ответственного и время создания. Действия: «Взять», «Освободить», «Сменить категорию», «Добавить участника», «Убрать участника», «Закрыть». Пользовательские и служебные действия проверяются по участнику и тикету, а не по видимости кнопки.

Пользовательские состояния: «Открыт», «В работе», «Ожидает ответа», «Закрыт». Технические стадии создания и закрытия сохраняются отдельно, чтобы интерфейс показывал незавершённую операцию, а не выдавал её за завершённую.

Одновременное взятие разрешается условным обновлением SQLite: ответственный назначается один раз. Смена категории согласует карточку, роль доступа и размещение канала; до завершения изменения не заявляются успешно применёнными.

## 6. Служебная ветка

Выделенный закрытый текстовый канал команды содержит карточки обращений. В нём бот создаёт настоящие private threads; родитель не является пользовательским каналом тикета. Поэтому удаление пользовательского канала не уничтожает служебное обсуждение.

Доступ к служебному каналу получают полная роль Ticket, роль просмотра и бот. Бот создаёт ветку, отключает свободное приглашение участников и управляет её членством. Сотрудник нажимает кнопку «Служебное обсуждение»; перед добавлением проверяются актуальные роли и отсутствие совпадения с автором тикета. После добавления бот возвращает личную ссылку.

Обычным Ticket-ролям не выдаётся `ManageThreads`, позволяющий видеть чужие приватные ветки. Такой подход не требует перечислять всех участников роли или автоматически подписывать их на каждую ветку. Права родительского канала должны сохранять это ограничение. Если служебная конфигурация не обеспечивает требуемую приватность, модуль сообщает об ошибке конфигурации.

Служебная переписка имеет отдельную область хранения. В веб-транскрипте — отдельная вкладка «Обсуждение команды». Запросы её сообщений и вложений дополнительно проверяют ограничение для автора обращения.

При закрытии ветка архивируется и блокируется для обычной записи. По истечении 180 дней удаляется вместе с остальным архивом. Прямые ручные изменения в Discord отражаются в журнале и процессе восстановления, когда бот получает соответствующие события.

## 7. Веб-транскрипт

Список обращений поддерживает фильтры по номеру, статусу, категории, автору, ответственному и датам. Карточка открывает хронологическую переписку с авторами и временем, вложениями, отметками правок и удалений, а также историей действий.

Переписка сохраняется по мере получения событий. Финальный сбор при закрытии сверяет оставшиеся сообщения и вложения с Discord. Файлы копируются в постоянное хранилище: архив не полагается на бессрочность CDN-ссылок. Отдельно сохраняются метаданные загрузки, размер, тип, состояние копирования и связь с областью доступа.

Для содержимого сообщений нужен intent `MessageContent`, для событий — `GuildMessages`. Использование ограничивается зарегистрированными тикет-каналами и их служебными ветками. Обычные каналы сервера в архив не записываются. Сбор переписки тикетов является новым согласованным назначением; прежний общий журнал действий остаётся отдельным механизмом.

Полнота ограничена полученными событиями: нельзя восстановить содержимое сообщения, удалённого во время отсутствия бота, если оно ранее не было сохранено. После восстановления соединения догружаются доступные сообщения; известные промежутки отмечаются, а не скрываются. История правок сохраняется с момента начала наблюдения.

HTML пользователя не исполняется. Markdown и вложения отображаются безопасно; получение файлов требует авторизации и проверки соответствующего тикета и области. Ограничения размера и дискового хранения настраиваются отдельно от прежнего редактора сообщений; непринятый файл явно помечается, а не считается сохранённым.

## 8. Закрытие, восстановление и срок хранения

Закрытие требует причины, подтверждения и актуальных прав. Тикет переходит в техническое состояние закрытия; повторная команда присоединяется к этой операции.

Порядок:

1. Прекратить обычную переписку в пользовательском канале.
2. Сверить и сохранить переписку, историю и требуемые вложения.
3. Сохранить финальные сведения о закрытии и служебной ветке.
4. Архивировать и заблокировать служебную ветку.
5. Удалить пользовательский канал после подтверждения готовности архива.
6. Зафиксировать завершение и срок удаления — 180 дней от времени закрытия.

Ошибка сохранения архива не приводит к удалению пользовательского канала. Несохранённые вложения или недоступные сообщения имеют явный статус и доступны для повторной попытки. Удаление канала и архивация ветки используют сохраняемые задания, чтобы продолжиться после рестарта без повторного создания ресурсов.

Фоновое удаление по сроку охватывает записи оперативного архива, правки, удаления, вложения, поисковые данные и служебную ветку Discord. Сначала закрывается веб-доступ по сроку, затем выполняются удаление Discord-ветки и очистка данных с повторными попытками. Сбой Discord не возвращает просроченный веб-доступ и не отмечается успешным удалением ветки. Итоговые обезличенные показатели не содержат переписки и могут остаться в агрегированной статистике.

Резервные копии и внешние журналы имеют собственный срок хранения: наличие старой копии не обещается устранить удалением текущего архива. Документация описывает это отдельно. После восстановления старой базы просроченный архив не выдаётся пользователям; очистка возобновляется.

## 9. Надёжность и журнал

Операции создания, назначения и закрытия используют транзакции и сохраняемые состояния. Discord API и SQLite не образуют общей транзакции: канал помечается стабильным идентификатором операции, чтобы восстановление могло найти уже созданный ресурс после неопределённого результата запроса.

Хранятся ID канала, начальной карточки, служебного родителя, ветки, панели и незавершённых операций. Кнопки остаются обрабатываемыми после рестарта. Удалённые вручную ресурсы получают явное состояние; модуль не создаёт второй канал автоматически без проверки.

Ошибки направляются в существующие ErrorReporter, `LOG_ID` и `LOG_WEBHOOK`. События управления фиксируют автора, время, действие и изменения. Общий журнал не становится второй бесконтрольной копией текста тикетов: содержимое переписки хранится в отдельном архиве с его правами и сроком.

## 10. Metrics

Схема: модули → общий интерфейс телеметрии → отдельный Metrics-процесс → Prometheus → существующая Grafana.

Core предоставляет неблокирующий интерфейс счётчиков, наблюдений длительности и текущих состояний. Опциональный Metrics-модуль экспортирует их через отдельный HTTP endpoint. Ошибка экспортёра не прерывает команды, публикации или работу Ticket. Передача между процессами ограничена по размеру и очереди; имена и метки определяются реестром.

| Область              | Показатели                                                                                                                                |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Core                 | Готовность, uptime, Gateway latency, переподключения, перезапуски, состояния модулей.                                                     |
| Процессы             | CPU, память, heap, event loop по роли процесса.                                                                                           |
| Команды и компоненты | Число вызовов, исход, длительность по модулю, команде или типу действия.                                                                  |
| Web                  | Запросы, коды ответа, длительности по шаблону маршрута.                                                                                   |
| Info и сообщения     | Публикации, отправки, ошибки и длительности операций.                                                                                     |
| Ticket               | Создания и закрытия, текущие статусы, очередь без ответственного, первое сообщение поддержки, время решения, ошибки архивации и удаления. |
| Очереди              | Размеры и возраст очередей журнала, ошибок и заданий Ticket.                                                                              |

Используются счётчики, gauges и histograms с секундами и байтами в именах. Метки ограничены: модуль, команда/действие, исход, статус и управляемая категория. ID пользователей и тикетов, имена, тексты, сырые URL и сообщения ошибок метками не становятся.

Бизнес-итоги тикетов вычисляются из согласованных данных SQLite или сохраняемых агрегатов; рестарт экспортёра не стирает сведения об обращениях. Счётчики процесса могут сбрасываться при его рестарте, что учитывается запросами Prometheus. Исторические ряды хранятся существующим Prometheus по его собственной политике.

Первый ответ поддержки — первое сообщение человека с правами поддержки в пользовательском канале после создания тикета. Сообщения бота и служебное обсуждение в это время не включаются. Время решения считается от создания до закрытия; повторные попытки технических операций не увеличивают число созданных и закрытых обращений.

Настройки: включение Metrics, bind/port и отдельный bearer token для scrape. Endpoint не использует браузерную OAuth-сессию. В Docker он публикуется по умолчанию на loopback; для внешнего Prometheus настраивается доступ через доверенную сеть. HTTP-порт панели и `/api/health` сохраняют своё назначение.

Поставляются dashboard JSON с выбором существующего Prometheus datasource и пример scrape-конфигурации. Основные экраны: обзор бота, здоровье модулей, команды/ошибки, Web, тикеты/время ответа, очереди/архивация. Новые контейнеры Grafana и Prometheus не добавляются.

## 11. Интеграционные изменения

- Registry модулей получает Ticket, а supervisor — опциональную роль Metrics.
- Реестр взаимодействий расширяется на select menus и modal submissions. Показ формы выполняется до defer; длительная работа подтверждается вовремя.
- Авторизация Web разделяется на общие и Ticket-разрешения; начальная загрузка UI зависит от них.
- Общая модель кнопок получает действие создания тикета; произвольные custom ID в пользовательский JSON не открываются.
- Добавляются миграции, таблицы конфигурации, тикетов, сообщений/редакций, файлов, событий и сохраняемых заданий.
- Постоянный Docker-том, backup/restore и проверки конфигурации учитывают архив и Metrics.
- `/help` получает команды Ticket из того же реестра. Начальный набор: создание обращения, личный список активных обращений и административная публикация панели. Работа внутри тикета остаётся доступна кнопками.

## 12. Приёмка следующего этапа

- Роль просмотра входит в архив и не получает доступ к настройкам или посторонним API.
- Полная Ticket-роль управляет Ticket без автоматической выдачи общих прав панели.
- Автор не получает служебную переписку через Discord, веб-страницу, экспорт или URL вложения при обычных правах Discord.
- Повторный клик и одновременное взятие не создают дубликаты и двух ответственных.
- Канал не удаляется до завершения необходимой архивации.
- Архив доступен в вебе после удаления пользовательского канала и переживает рестарт.
- По окончании 180 дней закрывается веб-доступ, удаляются текущий архив и служебная ветка; сбои удаления повторяются.
- Метрики охватывают процессы и модули, не содержат переписки/ID в метках и не блокируют функции бота.
- Dashboard импортируется в существующую Grafana с выбором datasource.
