## Открытые замечания

### [P2] Сериализуйте редактирование одного сообщения — src/server/composer-routes.ts:154

Два запроса PUT одного ID выполняют Discord PATCH и SQLite UPDATE без общей блокировки или версии. Если Discord уже применил A, затем B, но ответ A пришёл позже B, в Discord остаётся B, а история SQLite перезаписывается A. Воспроизведено через настоящий API приложения и управляемые ответы FakeDiscord: оба запроса успешны, `discordContent=B`, `sqliteContent=A`. Нужны последовательное редактирование по ID и защита от устаревшего редактора; одна общая блокировка публикаций эту операцию не покрывает.

### [P2] Не подменяйте версию открытого черновика фоновым ответом — src/web/Composer.tsx:133

Отправка сообщения и создание/удаление шаблона заменяют `workspace`, включая версию общего черновика, но оставляют локальные `document` и `baseline` прежними. Если другая вкладка уже сохранила новую версию, такой побочный запрос незаметно обновляет ожидаемую версию устаревшего редактора. Следующее сохранение проходит вместо 409 и перезаписывает чужие правки. Версию редактора следует хранить вместе с тем документом, который был загружен или сохранён; обновление списков истории/шаблонов не должно менять её.

### [P2] Применяйте результат загрузки к актуальному блоку — src/web/BlockEditor.tsx:197

Обработчик UploadButton после `await uploadMedia` вызывает onUpload из старого рендера. Этот callback замыкает прежние `value`, `block`, индекс и массив `blocks`. Во время загрузки остальные поля и перемещение блоков доступны. Если изменить подпись/другой пункт или переместить блок до ответа сервера, завершение загрузки возвращает старый массив и теряет новые изменения. Нужна адресация стабильным ID и функциональное обновление актуального дерева; второй вариант — блокировать редактирование на всё время загрузки, но он ухудшает UX.

### [P2] Оставьте списку страниц доступную область прокрутки — src/web/style.css:250

При проверке рабочего редактора на 1265×720 список из шести страниц имел высоту 17 px при scrollHeight 346 px. Фиксированные верхние и нижние разделы sidebar сжимают основную навигацию до полоски. Нужна прокрутка всей навигации либо более компактные фиксированные области с минимальной полезной высотой списка. Это мешает выбирать и переставлять страницы при обычной высоте окна.

### [P3] Верните контраст метке APP — src/web/style.css:628

У `.app-tag` фон `var(--accent)` и текст `var(--ink)` после каскада имеют одинаковый цвет `rgb(244,244,242)`. Метка выглядит пустым белым прямоугольником в предпросмотре правил, информации и сообщений. Для текста подходит существующий `--on-accent`.

## Исправлено при согласованной переработке журнала

- **[P2] Экспорт блокировал сохранения.** SQLite `.iterate()` оставался активным между yield потокового ответа. Параллельная транзакция того же соединения падала с `This database connection is busy executing a query`. Теперь экспорт выбирает порции через `.all()` и освобождает statement до yield. Есть регрессионная проверка.
- **[P2] Старый неисправный канал блокировал все новые логи.** Очередь каждый раз выбирала самые старые записи, получала ошибку старого канала и повторяла их бесконечно, даже после выбора исправного канала. Задержка повтора теперь назначается отдельно каждому каналу. Есть регрессионная проверка.
- Запись отдельного события больше не делает SELECT настроек + отдельный INSERT + SELECT результата. События собираются через outbox/Redis и сохраняются пакетами; UUID защищает от повторов.

## Безопасность и ограничения проверки

Обход авторизации, CSRF, SQL-инъекция или выполняемый HTML в Markdown не подтверждены. Это результат проверки, а не гарантия отсутствия всех уязвимостей. Проверены cookie-bound одноразовый OAuth state, серверная проверка роли, безопасная работа с локальными UUID медиа, параметризованные SQL-запросы, отключённый HTML Markdown и сокрытие секретов. Реальные токены не включались в отчёт и Git.

До изменений типизация, сборка и 15 тестов прошли; npm audit не сообщил известных уязвимостей. После Redis: сборка, типизация, форматирование и 19 тестов прошли, интеграционный тест Redis явно пропущен; npm audit — 0 известных уязвимостей. Автотесты используют FakeDiscord; продакшен-сервер Discord не использовался для проверочных отправок. Настоящий Redis проверяется отдельным тестом с TEST_REDIS_URL и Redis-сервисом в CI. Локально Docker Engine не работает из-за известной проблемы виртуализации: контейнерные проверки не выполнялись. Основной Compose и вариант HTTPS проверены статически через config --quiet; для HTTPS использован фиктивный DOMAIN без изменения .env.

Остаточные риски: открытые замечания выше, отсутствие тестов supervisor/ModuleManager на реальные процессы и Gateway, недостаточное покрытие конкурентных операций и браузерных сценариев загрузки файлов. Ticket и Metrics существуют пока как согласованный проект, не как реализованные модули. Намеренно выбранные AL-S тема, шрифты, фон и логотип не считаются дефектами.
